# Test Coverage and Limits

Run from the repository root using Python 3.10+:

```sh
python -m unittest discover -s tests -v
```

`test_reference_model.py` covers proposal scenarios T1-T11 functionally and the safe-state part of T12. It also checks fixed event bytes, command-field authentication, invalid-HMAC replay-state poisoning, unknown commands, default deny, anchored rewrites, checkpoint extensions/device binding, the unanchored truncation limitation, sequence maximum and event-counter exhaustion.

Known-answer fixtures include SHA-256 of `abc` and an HMAC-SHA256 example; these are fixed expected bytes, not expected outputs generated by the tested method. They check the software primitive/encoding baseline and are not evidence about an RTL SHA core.

| Coverage | Current evidence |
| --- | --- |
| T1-T3 | Model digest/version decisions and inactive output |
| T4-T9 | Model authentication/freshness/policy, reason, replay state, event/head update |
| T10 | Record modification, reordered records and recomputed anchored-history rejection |
| T11 | 105→104 truncation, checkpoint head/device mismatch and valid extensions |
| T12 | Reset between atomic calls clears safe state and prevents use of old trust; reset mid-RTL-transaction remains planned |

Test output generated by an actual run is the source of pass/fail results. No simulated waveform, synthesis report, timing benchmark or hardware result is supplied. Tests are kept independent of document validation; [the repository validator](../tools/validate_repository.py) checks links, mandatory content, DOI count and PNG structure.

Future cocotb tests should be added only alongside real RTL. They must include scheduler contention, locked-register behavior, handshake/backpressure, counter rollover, incomplete messages and reset at each transaction stage. Follow [the verification plan](../docs/verification-plan.md), rather than treating these software tests as complete hardware acceptance.
